## 2. Модули

| Модуль | Ответственность |
|---|---|
| `config.js` | 6 сетей в двух режимах (testnet/mainnet), RPC/эксплореры/краны, лимиты, URL превью |
| `keystore.js` | 32-байтные ключи: из env (KMS в проде) или из локальных файлов `0600` |
| `vault.js` | Создание/открытие зашифрованного BIP-39 mnemonic; деривация ключей; экспорт |
| `auth.js` | Валидация `initData` по спецификации Telegram; HMAC-сессии; гостевой вход |
| `db.js` | Пользователи, индексы деривации, транзакции, адресная книга, аудит |
| `chains/*` | Балансы, симуляция, подпись/отправка, статусы, курсы |
| `risk.js` | Лимиты в USD, белый список, эвристика address poisoning |
| `routes/api.js` | REST API, двухшаговое подтверждение, своп, настройки |
| `bot.js` | Telegram Bot API long polling, команды, WebApp-кнопка |
| `public/app.js` | UI, состояние, модалки, QR, Telegram SDK |

## 3. Криптография и деривация

Один зашифрованный master seed (BIP-39, 24 слова, 256 бит энтропии) → детерминированные дочерние ключи по индексу пользователя из БД. Индекс выдаётся атомарно, коллизии исключены.

| Цепь | Алгоритм | Путь | Адрес |
|---|---|---|---|
| EVM ×4 | secp256k1 / BIP-44 | `m/44'/60'/0'/0/{index}` | `0x…` (один на все EVM-сети) |
| Bitcoin | secp256k1 / BIP-84 | `m/84'/{0\|1}'/0'/0/{index}` | P2WPKH bech32 (`bc1` / `tb1`) |
| Solana | ed25519 / SLIP-0010 | `m/44'/501'/{index}'/0'` (hardened) | base58 публичного ключа |

Шифрование: `AES-256-GCM`, случайный IV 12 байт на запись, auth tag проверяется при открытии. Ключ (`VAULT_KEY`) и шифртекст (`vault.enc`) хранятся **раздельно**. Plaintext mnemonic существует только в памяти процесса.

## 4. Поток отправки (ключевая фишка безопасности)

```
1. Клиент: POST /api/simulate { chain, to, asset, amount }
2. Сервер: riskCheck → лимиты/whitelist/антифишинг
3. Сервер: simulate* → eth_estimateGas + eth_call / UTXO-планирование / getBalance
           → человеку понятный превью: метод, комиссия, флаги риска
4. Сервер: confirmToken = HMAC(SESSION_KEY, {uid, chain, to, asset, amount, exp 120s})
5. Клиент показывает превью и кнопку «Подписать и отправить»
6. Клиент: POST /api/send { …те же параметры…, confirmToken }
7. Сервер: сверяет токен И параметры (подмена → 400), повторяет riskCheck и simulate
8. Сервер: подписывает приватным ключом пользователя и транслирует в сеть
9. Статус pending → confirmed/failed обновляется лениво через /api/activity
```

Ни одна транзакция не подписывается без шага 3. Токен подтверждения криптографически связывает превью с подписываемыми данными.

## 5. Хранилище данных

`data/db.json` (атомарная запись через tmp+rename, права 0600):

```json
{
  "seq": 1,
  "users": { "tg_123": { "index": 1, "settings": {...}, "addressBook": [] } },
  "txs": [ { "id", "userId", "chain", "hash", "amount", "status", "simulated" } ],
  "audit": [ { "userId", "action", "detail", "at" } ]
}
```

В базе **нет приватных ключей** — они выводятся из seed на лету. Для продакшена замените на PostgreSQL + шифрование на уровне БД и вынесите аудит в append-only лог.

## 6. Сети

| ID | Testnet | Mainnet (после `ALLOW_MAINNET=true`) | Тип |
|---|---|---|---|
| `ethereum` | Sepolia, chainId 11155111 | Ethereum, 1 | EVM + USDC |
| `base` | Base Sepolia, 84532 | Base, 8453 | EVM + USDC |
| `arbitrum` | Arbitrum Sepolia, 421614 | Arbitrum One, 42161 | EVM |
| `polygon` | Amoy, 80002 | Polygon PoS, 137 | EVM |
| `bitcoin` | Testnet4, mempool.space | Mainnet | UTXO / PSBT |
| `solana` | Devnet | Mainnet-beta | ed25519 |

Все балансы запрашиваются параллельно через `Promise.allSettled` — недоступная сеть не роняет весь портфель, а помечается красным индикатором.

## 7. Масштабирование

- Вынести подпись в отдельный воркер с KMS/HSM и очередью (BullMQ/Redis).
- JSON → PostgreSQL; сессии → Redis с TTL.
- Горизонтальное масштабирование API (stateless), воркер подписи — singleton с mutex.
- Кэш курсов и балансов (60 с), websocket для статусов транзакций.
- Метрики/алерты: Prometheus + Grafana, алерт на любой `keys.exported` и на отклонения лимитов.
