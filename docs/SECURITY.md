# Безопасность NOVA Wallet

Дата: 25.10.2026 · статус: **MVP, testnet по умолчанию**

Это самый важный документ проекта. Прочитайте его до включения mainnet.

## 1. Честная модель угроз

Кошелёк **кастодиальный**: сервер владеет master seed и подписывает транзакции от имени пользователя. Это даёт удобство («без сид-фразы»), но создаёт централизованную точку отказа.

| Угроза | Риск | Что сделано сейчас | Что нужно до продакшена |
|---|---|---|---|
| Компрометация сервера/процесса | Критический | Ключи в памяти, шифртекст отдельно от ключа | KMS/HSM, подпись в изолированном воркере, egress-фильтрация |
| Утечка `.env` / бэкапа | Критический | Файлы 0600, исключены из архивов и git | Секреты только в KMS, ротация, шифрованные офлайн-бэкапы |
| Подмена транзакции (MITM/UI) | Высокий | Двухшаговое подтверждение с HMAC-токеном | Аппаратное подтверждение, нотификации с антифишинг-кодом |
| Кража сессии | Высокий | HMAC-сессии, 7 дней, проверка подписи | Привязка к `initData`, короткий TTL, refresh, device binding |
| Дрaйнер / фишинг адреса | Высокий | Симуляция, декодирование метода, эвристика совпадения начала/конца адреса | Реестр известных скам-адресов, проверка контракта, allowlist по умолчанию |
| Превышение лимитов | Средний | Per-tx и дневной лимит в USD | Лимиты на стороне KMS, задержка на крупные суммы, ручное одобрение |
| Откат/потеря БД | Средний | Атомарная запись, детерминированная деривация (адреса восстанавливаются) | Репликация, PITR-бэкапы, проверка восстановления |
| Rate limiting / DoS | Средний | Лимит тела запроса 64 КБ | Rate limiting, WAF, капча на чувствительные методы |
| Утечка ключа через экспорт | Средний | Явное подтверждение фразой + аудит | Запретить экспорт в проде / только через KMS-процедуру |

## 2. Реализованные контроли

1. **Шифрование на диске.** `AES-256-GCM`, IV 12 байт, auth tag. Ключ `VAULT_KEY` (32 байта) отдельно от `vault.enc`.
2. **Валидация Telegram `initData`.** `HMAC-SHA256` с секретом, производным от токена бота; `timingSafeEqual`; проверка свежести `auth_date` (24 ч).
3. **Сессии.** HMAC-подпись payload, проверка срока жизни, постоянное время сравнения.
4. **Двухшаговое подписание.** Симуляция → `confirmToken` (HMAC, TTL 120 с) → повторная проверка параметров → подпись. Подменить получателя/сумму между экранами невозможно.
5. **Симуляция перед подписью.** `eth_estimateGas` + `eth_call`, проверка кода получателя (контракт), баланса, UTXO и комиссий; для BTC — планирование входов/сдачи; для SOL — проверка лампортов.
6. **Лимиты.** Per-tx ($250) и дневной ($1000) в USD по живым курсам; настраиваются пользователем.
7. **Белый список адресов.** Опциональный режим «только проверенные адреса».
8. **Анти-отравление адресов.** Блокировка, если адрес получателя совпадает с вашим по первым 6 и последним 4 символам.
9. **Аудит.** Логин, отправки, смена настроек, экспорт ключей — с временем и деталями.
10. **Testnet по умолчанию.** Mainnet только при явном `ALLOW_MAINNET=true`; гостевой вход в mainnet отключён.
11. **Гигиена секретов.** `.gitignore`, `.env` 0600, ключи и БД не попадают в архивы Drive.

## 3. Известные ограничения (не скрываем)

- **Нет независимого аудита.** Код написан и протестирован автором проекта; формального security review не было.
- **Нет KMS/HSM.** В превью ключ лежит в `.env` или файле `data/vault.key` на той же машине, что и шифртекст. Для продакшена это неприемлемо.
- **Нет rate limiting и WAF.**
- **JSON-БД** без блокировок между процессами; подходит только для одного инстанса.
- **Своп в mainnet отключён** (возвращает 501) — требуется аудированный агрегатор и approval-флоу.
- **Публичные RPC/краны** нестабильны и лимитированы; для продакшена нужны платные провайдеры.
- **Нет KYC/AML и юридического комплаенса** — обязательно для кастодиального сервиса в большинстве юрисдикций.
- **Нет страхования/резервного фонда.**

## 4. Чек-лист перед mainnet

- [ ] Независимый аудит кода и пентест (включая подписывающий воркер).
- [ ] `VAULT_KEY` и `SESSION_SECRET` только в KMS (AWS KMS / GCP KMS / HashiCorp Vault), ротация.
- [ ] Подпись вынесена в изолированный сервис без исходящего интернета, с белым списком RPC.
- [ ] Офлайн-бэкап `vault.enc` + процедура восстановления, проверенная на тесте.
- [ ] PostgreSQL с шифрованием, репликацией и PITR; Redis для сессий.
- [ ] Rate limiting (например, 5 отправок/мин), WAF, мониторинг и алерты.
- [ ] Пороговые подписи (MPC / Shamir) или multisig вместо одного seed.
- [ ] Юридическая экспертиза: лицензии, KYC/AML, пользовательское соглашение, GDPR.
- [ ] Политика инцидентов: пауза выводов (circuit breaker), уведомление пользователей.
- [ ] Страховой/резервный фонд и прозрачный proof-of-reserves.

## 5. Обращение с секретами

**Можно коммитить/загружать в Drive:** исходники, документацию, тесты, `.env.example`, архивы без `data/` и `.env`.

**Нельзя:** `.env`, `data/vault.key`, `data/session.key`, `data/vault.enc`, `data/db.json`, любые приватные ключи и сид-фразы, логи с адресатами.

Архивы в Google Drive собраны именно так: код и документы — да, секреты — нет. Если вы разворачиваете проект заново, `npm run setup` создаст **новый** seed: старые адреса и средства будут потеряны, если не сохранить `vault.enc` и ключ.

## 6. Инцидент-респонс (минимальный)

1. Немедленно выставить `ALLOW_MAINNET=false` и остановить подписывающий воркер (circuit breaker).
2. Отозвать/ротировать `SESSION_SECRET`, `BOT_TOKEN`, `VAULT_KEY`.
3. По аудит-логу определить затронутые аккаунты и хеши транзакций.
4. Уведомить пользователей через бота с антифишинг-кодом.
5. Средства перевести на новый холодный vault (процедура готовится заранее).
