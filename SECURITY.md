# 🔐 Security Policy

## ⚠️ Сначала главное

**NOVA Wallet — это TESTNET MVP без независимого аудита с кастодиальной моделью ключей.**
Не используйте его для реальных средств. `ALLOW_MAINNET=false` выставлен в `.env.example`
намеренно. Если вы всё же включаете mainnet, вы делаете это на свой страх и риск.

## Поддерживаемые версии

| Версия | Поддержка |
|---|---|
| `1.0.x` | ✅ исправления безопасности |
| `< 1.0` | ❌ нет |

Обновления выходят в виде тегов `v1.0.x`; см. [CHANGELOG.md](CHANGELOG.md).

## Как сообщить об уязвимости

**Пожалуйста, не открывайте публичный Issue для уязвимостей.** Это подвергает риску
пользователей, которые уже запустили тестовый кошелёк.

Порядок действий:

1. Откройте **приватный** [Security Advisory](https://github.com/AlekseyZHL/NOVA/security/advisories/new)
   (вкладка Security → Report a vulnerability).
2. Если это невозможно — напишите мейнтейнеру через GitHub Profile с пометкой
   `SECURITY: NOVA Wallet` и попросите приватный канал связи.
3. Не публикуйте эксплойт, приватные ключи, `.env`, `vault.enc` и дампы `db.json`
   ни в issue, ни в PR, ни в публичных чатах.

### Что указать в отчёте

- Компонент: `server/auth.js`, `vault.js`, `chains/*`, `middleware/risk.js`, `public/app.js` …
- Тип проблемы и предполагаемое влияние (кража ключей, обход лимитов, подмена `confirmToken`, XSS …).
- Минимальные шаги воспроизведения / PoC **без реальных секретов**.
- Версия Node.js, `MODE` (testnet/mainnet), конфигурация.

### Чего ждать

- Подтверждение получения — в течение **72 часов**.
- Первичная оценка и план — в течение **7 дней**.
- Мы попросим вас не раскрывать детали до выхода фикса; дату публикации согласнуем вместе.

Проект не имеет программы bug bounty — вознаграждение не гарантируется, но мы обязательно
укажем вас в `CHANGELOG.md` (с вашего согласия).

## Что уже защищено

| Механизм | Где |
|---|---|
| `initData`: HMAC-SHA256 + `timingSafeEqual`, проверка `auth_date` (24 ч) | `server/auth.js` |
| Сессии: HMAC, 7 дней, подделка отклоняется | `server/auth.js` |
| Master seed: BIP-39 24 слова, AES-256-GCM, ключ отдельно от шифртекста | `server/vault.js`, `server/keystore.js` |
| Подтверждение: HMAC-токен на `{u,c,t,a,m,e}`, TTL 120 с, повторная проверка параметров | `server/routes/api.js` |
| Лимиты, белый список, anti-poisoning | `server/middleware/risk.js` |
| Симуляция перед подписью | `server/chains/*` |
| Гостевой вход автоматически выключен в mainnet | `server/config.js` |
| Секреты не попадают в Git (`.gitignore` + `scripts/check-secrets.sh` в CI) | `.github/workflows/ci.yml` |

## Известные риски (принятые осознанно)

1. **Кастодиальность.** Компрометация сервера = компрометация всех ключей. Нужен KMS/HSM + аудит.
2. **JSON-файл вместо БД.** Нет транзакционности и блокировок при конкурентной записи. Нужен PostgreSQL.
3. **Нет rate limiting.** Возможен перебор и спам рассылками. Нужен reverse-proxy / Redis.
4. **Публичные RPC.** Зависят от доступности и лимитов сторонних провайдеров.
5. **Нет аудита.** Криптография использует проверенные библиотеки, но связующий код не ревьюился.
6. **`DEMO_AUTH=true`** в тестнете разрешает гостевой вход — это удобно для превью, но не для продакшена.
7. **Mainnet-своп отключён** (`501`) до подключения аудированного DEX-агрегатора.

## Операционная гигиена

- Храните `.env` с правами `0600`, бэкапьте `.env` **и** `data/vault.enc` офлайн, в шифрованном виде.
- Никогда не коммитьте `BOT_TOKEN`, `VAULT_KEY`, `SESSION_SECRET`, `MASTER_MNEMONIC`.
- Ротируйте токен бота через @BotFather `/revoke`, если он где-то засветился.
- Экспорт приватных ключей (`/api/export`) требует явного согласия и пишется в аудит-лог.
